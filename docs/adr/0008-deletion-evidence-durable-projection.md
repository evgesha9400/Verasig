# Deletion evidence is a durable, first-class projection — observed by live rescan, not recomputed

`DeletedSignalEvidence` is produced by a new pure `services/deletion/` detector and a gated rescan, and is **persisted** (migration `0005` + `DeletedSignalEvidenceRow` + a repo upsert). A deletion is found by **re-fetching the channel's current live message-id set** (a new `TelegramSource.live_message_ids`) and diffing it against the durable **stored** set, over `range = [min..max]` of `stored ∪ live`: `CONFIRMED`/`SNAPSHOT_DIFF` = `stored − live` (the message we captured is gone now — `original_text` + `first_seen_at` retained); `SUSPECTED`/`ID_GAP` = `range − stored − live` (a slot present in **neither** snapshot — never captured, now gone, no content). One row per `(channel_id, message_id)`: rescans are idempotent (`+0`), a `SUSPECTED` may upgrade to `CONFIRMED` but a `CONFIRMED` never downgrades, and the first-noticed `detected_at` is preserved. **All** confirmed deletions are stored for audit; only `was_signal_candidate` ones feed the Slice-8 deletion-behaviour score, and `SUSPECTED` is surfaced per channel.

We did this because raw capture is **insert-only** (`raw_telegram_message` is appended with `ON CONFLICT DO NOTHING` and backfill resumes from a cursor), so a deleted message **never leaves our DB** — the plan's "two backfill snapshots" can never reveal a deletion by comparing two *stored* copies. The only honest signal is **stored vs a fresh live re-fetch**. And unlike every other derived table, this evidence **cannot be recomputed**: the live snapshot it is diffed against is ephemeral and retained nowhere, so a later recompute would silently lose deletions. [ADR 0001](0001-two-layer-raw-capture.md) already kept `DeletedSignalEvidence` as a **first-class entity** (rejecting an event-sourced `DELETED` stream because it overlaps this), and [ADR 0007](0007-lifecycle-fold-pure-recomputable.md) already contrasted it with the recomputable fold ("retains `original_text` because the source *vanishes*"). This ADR formalizes it as the **third storage class**.

## Considered options

- **In-memory / recomputable** (symmetric with the fold, [ADR 0007](0007-lifecycle-fold-pure-recomputable.md)): rejected — the fold's sources are durable (append-only messages + recomputable signals), so it can be re-derived on demand; a deletion is observed against a **live snapshot that nothing retains**, so a recompute later would silently lose every deletion. Persisting the observation is the only honest record. This is precisely the line ADR 0007 drew.
- **Two stored backfills diffed** (the literal plan wording): rejected — insert-only capture + resume-from-cursor means a second backfill never re-reads or removes captured ids, so `diff(stored, stored)` is always empty. Detection requires a deliberate **full live re-fetch**, not a re-backfill.
- **Event-sourced `CREATED/EDITED/DELETED` stream** on `RawSignalEvent` ([ADR 0001](0001-two-layer-raw-capture.md)'s rejected option): still rejected — it overlaps this first-class entity and muddies the advisory candidate layer; keep `DeletedSignalEvidence` dedicated.
- **`SUSPECTED` = any gap in the stored id sequence** (offline, no re-fetch): rejected — service actions, media albums and polls all leave id gaps, flooding the Slice-8 deletion rate with non-deletions. Requiring **absent from both** (`stored` ∧ `live`) lets the live set **rescue** every still-present id (content *or* service action), so only genuinely-vanished slots remain `SUSPECTED`.
- **Reuse `backfill_batches(after=None)` for the live ids**: rejected — it pulls full message bodies for an ids-only need and overloads "backfill" (resume, never-rescrape) with its opposite (full re-fetch). A dedicated `live_message_ids` states intent and keeps the `FakeSource` trivial.
- **Drop chatter deletions at detection**: viable, but rejected — a complete audit trail ("provider wiped 50 messages, 5 were signals") is cheap to keep. The rule that chatter "affects nothing" is enforced at the **score/display** layer (only `was_signal_candidate` deletions score; chatter rows are never shown), which keeps the detector pure and complete and centralises the policy.

## Consequences

- **New contract:** `DeletedSignalEvidence` (`domain/deletion.py`) with `DeletionConfidence{CONFIRMED,SUSPECTED}` + `DeletionMethod{SNAPSHOT_DIFF,ID_GAP,LIVE_EVENT}`; the entity matches frozen [data-contracts §6](../work/stage-0-local-observer/data-contracts.md) 1:1. Coupling: `SNAPSHOT_DIFF→CONFIRMED` (+`original_text`, +`first_seen_at`=stored `captured_at`), `ID_GAP→SUSPECTED` (no content), `LIVE_EVENT→CONFIRMED` (Slice 10).
- **New seam:** `TelegramSource.live_message_ids(channel_id) -> set[int]` (amends [data-contracts §9](../work/stage-0-local-observer/data-contracts.md)); `TelethonSource` projects ids from `iter_messages` (manual acceptance, never in tests); `FakeSource` returns a canned set.
- **Third storage class.** Append-only raw ([ADR 0001](0001-two-layer-raw-capture.md)) · recomputable projection ([ADR 0006](0006-extraction-outcomes-shape-and-lifecycle.md)) · in-memory recompute ([ADR 0007](0007-lifecycle-fold-pure-recomputable.md)) · now **durable, non-recomputable evidence** (this ADR). Idempotency: `UNIQUE(channel_id, message_id)`; the upsert upgrades `SUSPECTED→CONFIRMED` only (guarded), preserves the first-noticed `detected_at`, and re-run is `+0`.
- **Pure + offline core:** `services/deletion/diff.py` `detect_deletions(stored, live_ids, candidate_ids, detected_at) -> list[DeletedSignalEvidence]` takes lists/sets + an injected clock and returns evidence; the decisive tests use crafted id sets with **zero** Telegram/network. `detected_at` is a parameter (the model defaults `_now()`); `was_signal_candidate` is derived from `repo.candidate_message_ids` for `CONFIRMED`, `False` for `SUSPECTED`.
- **Gated orchestration:** `services/deletion/rescan.py` re-fetches the live id set, runs the pure diff, and persists — manual-acceptance only (no test touches real Telegram), mirroring `backfill.py`. It **aborts on an empty/failed live re-fetch** so an inaccessible channel is never misread as a mass deletion.
- **Surface:** gated `verasig rescan <ref>` (re-fetch + detect + store) + offline `verasig deletions <ref>` (read stored evidence: signal-`CONFIRMED` with text + a per-channel `SUSPECTED` count; chatter hidden). Mirrors the established gated-writer (`backfill`) vs offline-reader (`stats`/`lifecycle`) split.
- **Boundary:** no `LIVE_EVENT` (Slice 10), no scoring (Slice 8). Only signal-candidate confirmed deletions are scored; chatter is audit-only; `SUSPECTED` is per-channel display.
