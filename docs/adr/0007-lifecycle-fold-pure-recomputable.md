# The signal lifecycle fold is a pure, recomputable, in-memory view — modifications are not signals

The `Signal lifecycle` (an entry plus the later messages that move its stop, set its targets, scale it in/out, or close it) is folded into a `FoldedSignal` by a new pure `services/lifecycle/` function — `fold(entry_signals, messages, version) -> list[FoldedSignal]`. It reads the channel's `ExtractedSignal` entries **and** their `RawTelegramMessage`s, threads each entry's `reply_to` chain (transitively, symbol-guarded), classifies every reply as `MODIFY`/`CLOSE`, and accumulates the **effective** position state (stop, take-profits, size, average entry) into a time-ordered timeline keyed by message `posted_at`. The fold is **not persisted**: it carries a `fold_version` and is recomputed on demand by the scorecard and simulation. `SimOutcome.folded_signal_id` is just the `root_signal_id` (the `NEW_ENTRY`'s id).

We did this because a modification message (`"move SL to BE"`, `"add here"`, `"close half"`) usually carries no `side` and often no symbol, so it can **not** become an `ExtractedSignal` — the deterministic parser requires symbol+side, and minting one would need a placeholder `event_id` (the exact anti-pattern [ADR 0006](0006-extraction-outcomes-shape-and-lifecycle.md) rejected). The lifecycle therefore can't live in the extractors (which stay pure `text -> TradeIntent`), and the linkage it needs (`reply_to_message_id`) plus the true time axis (`posted_at`) live **only** on `RawTelegramMessage`. A dedicated fold pass over entries + raw messages is the only placement that satisfies all three constraints without corrupting the extraction projection.

## Considered options

- **Classify lifecycle in the extractor / LLM** (parser or fallback sets `event_type` + `references_message_id`): rejected — [ADR 0006](0006-extraction-outcomes-shape-and-lifecycle.md) made extractors deliberately pure `text -> TradeIntent` with no event linkage; replies lack `side` so the parser still returns `None`.
- **Pre-extract classify + inherit symbol/side** (late-materialize a `RawSignalEvent` per reply, inherit parent's symbol/side, persist `MODIFY`/`CLOSE` `ExtractedSignal`s): rejected — pollutes the events table and the one-of outcome projection with patch messages, reintroduces placeholder linkage, and forces the parser to handle non-signals.
- **Persist `FoldedSignal` as a recomputable projection table** (symmetric with [ADR 0006](0006-extraction-outcomes-shape-and-lifecycle.md) `record_outcome`): viable, but rejected — the fold adds **no new information** over its inputs, and unlike `DeletedSignalEvidence` (which retains `original_text` because the source *vanishes*) the fold's sources are durable (`raw_telegram_message` is append-only; `extracted_signal` is itself recomputable). A stored projection can only go stale; recompute over immutable inputs + a `fold_version` is strictly more honest and is the documented audit bar ("every score reconstructable from evidence").
- **`FoldStep.source_signal_id` only** (the frozen §5 shape): rejected — a modify step has no signal id. Keeping `source_signal_id` pinned to the durable `root_signal_id` **and** adding `source_message_id` gives every step a durable, append-only provenance anchor without phantom signals.
- **First-class `size`/`risk` field on `TradeIntent`**: rejected — it spills into the parser, the LLM prompt, storage, and scoring. Position changes always state a multiplier (`"close half"` = ×0.5, average-in = +1 same-size leg), so **equal-weight legs with stated multipliers** capture size deterministically with zero contract change.
- **Resolve market-price legs inside the fold** (inject a `MarketData` seam): rejected — pulls market data into the lifecycle fold. A leg posted `"at market"` (`leg_price = None`) is left pending and resolved against klines, exactly the existing `EntryType.MARKET` fill pattern.

## Consequences

- **New contracts:** `FoldedSignal` + `FoldStep` (`domain/lifecycle.py`), gaining `source_message_id`, per-step `event_type`, `effective_size`, `effective_entry`, `leg_size`, `leg_price`, and a `fold_version`. Amends [data-contracts §5](../work/observer/data-contracts.md); `§3 references_message_id` and `§8 folded_signal_id` comments are corrected to reflect the in-memory fold.
- **Widened term:** `SignalModification` now includes scaling in/out (averaging) by a stated multiplier, not just stop/target/close.
- **Pure + offline:** `fold(...)` takes lists, returns lists; the decisive tests use crafted threads with **zero** Telegram/LLM/market/network. A read-only `verasig lifecycle <ref>` CLI reads the DB, folds, and prints — no writes.
- **Auditability = recompute:** a past score is reproducible by re-running `fold` at the recorded `fold_version` over the immutable inputs; `ProviderScoreExplanation.evidence_refs` carry source message/signal ids + `fold_version`.
- **Market-data resolution:** `leg_price = None` (market legs) and the resulting `effective_entry = None` are filled from klines; `move SL to BE` resolves to the effective average entry, so a pending market leg leaves BE pending too.
- **Boundary:** lifecycle folding does not score, simulate, detect deletion, or ingest live events.
